## 宿主扩展能力

`AppPermission` 的三个内置值和既有方法签名保持不变。新增 String overload 接收宿主约定的能力 key，例如 `PHOTO_LIBRARY`；不把 `android.permission.*` 当作跨平台权限。未注册 key 的查询、申请和设置恢复均返回 `UNSUPPORTED`，其 `allowsUse` 为 false，宿主不应引导用户反复去设置页恢复未实现能力。

Android/iOS 在原生组合根包装既有 owner；core 不依赖 Kuikly：

```kotlin
import io.github.gycrosskit.permission.PermissionHandler
import io.github.gycrosskit.permission.PermissionPlatform
import io.github.gycrosskit.permission.PermissionRegistry

fun withPhotoLibrary(owner: PermissionPlatform, handler: PermissionHandler): PermissionPlatform =
    PermissionRegistry(owner, mapOf("PHOTO_LIBRARY" to handler))

// owner 仍由宿主创建和绑定；photoLibraryHandler 是当前平台的原生实现。
val permissions = withPhotoLibrary(owner, photoLibraryHandler)
val status = permissions.request("PHOTO_LIBRARY")
```

`PermissionHandler` 实现无参 `suspend getStatus()`、`request()`，以及可选的 `resumeAfterSettings()`（默认重读）。系统权限声明、线程切换、真实平台状态映射和系统弹窗取消屏障由 handler 负责。注册表复制传入 map，不缓存权限状态；空白 key、覆盖内置 key 或嵌套注册表中的重复 key 会在构造时抛出 `IllegalArgumentException`。Map 自身的重复键需由构造 map 的宿主处理。

Android 用 `exports.registerPermissionModule(permissions)` 注入；绑定/解绑仍操作原 `AndroidPermissionPlatform` owner。iOS 用 `IosPermissionModuleHandler(platform = permissions)` 注入，Swift `configure` 工厂和 receiver 无需新增 transport。Kuikly 页面可直接调用 `PermissionModule().request("PHOTO_LIBRARY")`；页面 Module 和原生 receiver 仍按原生命周期释放。扩展的设置恢复直接交给对应 handler，内置三种能力保留原平台策略。

HarmonyOS 使用 `GycPermissionHandler`，保持既有同步 `getStatus()` / `resumeAfterSettings()` 与异步 `request(context)`：

```typescript
import { GycPermissionService, GycPermissionModule, GycPermissionHandler } from '@gycrosskit/permission-native';

// photoLibraryHandler 是宿主的 HarmonyOS 实现，不会自动获得任何系统权限。
const handlers: Map<string, GycPermissionHandler> = new Map();
handlers.set('PHOTO_LIBRARY', photoLibraryHandler);
const permissions = new GycPermissionService(handlers);
const status = await permissions.request(context, 'PHOTO_LIBRARY');

// 用此无参类替换原 Module 表中 GycPermissionModule 对应的类；每 Renderer 新建 receiver。
class HostPermissionModule extends GycPermissionModule {
  constructor() { super(permissions); }
}
```

`GycPermissionService` 同样复制注册 map，拒绝空白与内置 key。扩展 `request(context)` 进入现有全局系统弹窗队列，页面取消只跳过尚未开始的申请；已开始的 handler Promise 必须等实际原生终态后完成，不能因调用方取消提前释放屏障。未注入时继续提供原有内置能力。

## Android 宿主

在宿主范围复用 `AndroidPermissionPlatform`。每个 `ComponentActivity` 创建时在主线程 `bind(activity)`，销毁时在主线程 `unbind(activity)`，同一 Activity 不得重复绑定。临时顶层 Activity 销毁后会恢复前一个绑定宿主；未绑定时查询/申请会等待宿主，调用协程应绑定页面生命周期。公开 suspend 入口内部切 Main；直接共享使用 `AndroidPermissionRequestHistory` 时，宿主也须在主线程读写同一实例。

按实际功能在 Manifest 声明 `android.permission.CAMERA`、`android.permission.RECORD_AUDIO`、`android.permission.ACCESS_COARSE_LOCATION`、`android.permission.ACCESS_FINE_LOCATION`。精确定位申请同时包含粗略定位。

`getStatus` 只读取状态；`request` 由用户操作触发；`resumeAfterSettings` 在 Android 的 `DENIED` 状态下可能再次申请，以兼容系统“每次询问”。不要把无 rationale 当作永久拒绝。解绑所属宿主会使挂起调用抛出异常；协程取消不能关闭系统弹窗，下次申请需等待真实回调或解绑。

已有权限历史保存在 SharedPreferences 时，用自有 namespace 构造：

```kotlin
val permissions = AndroidPermissionPlatform(historyPreferencesName = "legacy_permission_history")
```

保持旧 namespace 和权限枚举名（例如 `CAMERA`）即可，无需复制历史。默认 namespace 是 `gycrosskit_permission_history`；已授权事实始终以系统为准。

### 媒体权限执行器（自 0.1.2 提供）

```kotlin
val instanceHistory = AndroidPermissionRequestHistory()
val persistentHistory = AndroidPermissionRequestHistory(preferencesName = "legacy_permission_history")
val status = activity.requestRuntimePermission(android.Manifest.permission.CAMERA, instanceHistory)
```

默认 `AndroidPermissionRequestHistory` 只记录当前对象；picker 沿用实例范围，API 28 及以下保存相册的
WRITE_EXTERNAL_STORAGE 沿用宿主持有的进程范围对象。不要把这两种历史无条件改成持久化全局历史。
指定 namespace 时保持原 key；直接执行器以完整系统权限字符串为 key，`AndroidPermissionPlatform`
使用 AppPermission 枚举名，两者不能混用 key 来假装历史已经迁移。

`GRANTED` 和系统策略 `RESTRICTED` 直接返回；其余状态在用户主动操作时注册本次 RequestPermission launcher 并申请，
不因旧申请历史或无 rationale 跳过。一次授权失效后仍允许重新申请。内部以单元素 `RequestMultiplePermissions` 区分明确拒绝与空回执；申请前已是 `REQUESTED_WITHOUT_RATIONALE`、本次对应权限明确 false、回执后仍无 rationale 且无系统策略限制时，返回 `SETTINGS_REQUIRED`，宿主可提供设置恢复入口。这不是永久拒绝证明，后续仍允许再次申请。首轮拒绝、有 rationale 或空回执返回 `DENIED`，系统策略限制返回 `RESTRICTED`。旧 `REQUESTED_WITHOUT_RATIONALE` 本身不能作为设置提示依据。
取消在主线程注销所属 launcher，系统授权框仍只能由用户结束，迟到回调不会恢复旧协程或进入新请求。
结果到媒体枚举/页面提示的映射由宿主完成。独立消费样例见 verification-consumer 的 AndroidProbe。
Launcher 注册或启动异常向调用方传播，不伪装成用户拒绝；仅启动受理后记录历史。

## iOS

`IosPermissionPlatform()` 可在后台构造，公开 suspend 入口内部切换主线程，无需 UIViewController 绑定。Maven 0.1.8 中，取消可来自任意线程，但只取消调用方等待，不取消独立的原生请求 Deferred；后继请求须等相机、麦克风或定位的实际授权回调后才启动。旧回调只完成自己所属的 Deferred，不会交付给新请求；不能关闭已展示的系统权限弹窗。按功能填写 Info.plist 的 `NSCameraUsageDescription`、`NSMicrophoneUsageDescription`、`NSLocationWhenInUseUsageDescription`。声明文案由宿主提供，缺少声明可能被系统终止。定位精度状态使用 iOS 14 API，因此宿主最低部署版本需设为 iOS 14 或更高。

## HarmonyOS 原生与 Kuikly

安装根 README 的 OHPM 包，在 UIAbility 内使用：

```typescript
import { GycPermissionService, GycPermission, GycPermissionStatus } from '@gycrosskit/permission-native';
const permissions = new GycPermissionService();
const before = permissions.getStatus('CAMERA');
const status = await permissions.request(context, 'CAMERA');
const restored = permissions.resumeAfterSettings('CAMERA');
```

`context` 是当前 `UIAbilityContext`。在 `module.json5` 中按需声明 `ohos.permission.CAMERA`、`ohos.permission.MICROPHONE`、`ohos.permission.APPROXIMATELY_LOCATION`、`ohos.permission.LOCATION`；精确定位与粗略定位一起声明/申请。

Kuikly Kotlin Pager 注册 `PermissionModule.NAME to PermissionModule()`（包 `io.github.gycrosskit.permission.kuikly`）；ArkTS render 的 Module 表注册 `GycPermissionModule.MODULE_NAME` 对应 `GycPermissionModule`。每页持有自己的 Kotlin Module，页面结束时 `dispose()` 取消挂起调用并移除回调；不要在 dispose 后复用。

调用和 dispose 均在页面 Kuikly 协程上下文执行；沿用 120 秒权限等待和 request Mutex。
所有未完成桥调用（含可挂起的扩展 `getStatus`）在超时/取消时按 requestId 发送 `cancelQueued` 并移除 callback，使原生 handler 能执行 finally 释放监听；已显示的系统权限框屏障仍由平台 owner 保留。dispose 只结束组件拥有的等待，不接管页面 ViewModel，也不声称可以撤回系统授权框。

## Android/iOS Kuikly Native Module

本版源码提供 Maven `0.1.9`、Pod `GycPermissionKuikly/Kuikly` `0.1.9`；发布与远程消费状态以对应 Release 为准。历史 Maven `0.1.8` 的 `-kuikly` 仅含 OHOS 变体。Android API24+、iOS14+；使用 `com.github.gycrosskit.permission:permission-kuikly:0.1.9`。不改 Kuikly SDK；Kotlin handler 由宿主已有 Shared framework 导出。

Android 在宿主已有 `registerExternalModule` 接入点注册：

```kotlin
import io.github.gycrosskit.permission.kuikly.registerPermissionModule

// exports 是真实 IKuiklyRenderExport；每个 Renderer 由 SDK factory 新建 receiver。
exports.registerPermissionModule(permissionPlatform)
```

Android 复用宿主已迁移的 `AndroidPermissionPlatform(historyPreferencesName = "app_permission_history")`，保留旧 namespace；宿主已有 `gycrosskit_permission_history` 的 true 历史迁移保持原逻辑，本组件不另建 namespace 或重复迁移。Main 提前 `permissionPlatform.bind(activity)`，Activity 销毁时 `unbind(activity)`；iOS 在应用中复用同一 `IosPermissionPlatform`；Android 也复用同一权限 owner 并绑定当前 Activity，不能为每个 Renderer/窗口另建 owner。系统 prompt 无法因协程取消而关闭，owner 必须跨 Renderer 保留真实回执屏障。`resumeAfterSettings` 透传原生实现：Android DENIED 受控申请，iOS 只重读；OHOS 既有策略保持。

iOS 安装可选原生 Pod subspec，将 `permission-kuikly` 导出到宿主既有 Shared framework，随后在创建 Renderer 前于 Main 装配：

```kotlin
// 沿用宿主已有 framework，不新建组件 framework；依赖须为 api 才能 export。
commonMain.dependencies {
    api("com.github.gycrosskit.permission:permission-core:1.0.0")
    api("com.github.gycrosskit.permission:permission-kuikly:1.0.0")
}
// 放入宿主已有 iOS framework 配置：
export("com.github.gycrosskit.permission:permission-core:1.0.0")
export("com.github.gycrosskit.permission:permission-kuikly:1.0.0")
```


```ruby
# 对应 Release 公开后固定精确 tag；远程消费状态需单独核实。
pod 'GycPermissionKuikly/Kuikly', :git => 'https://github.com/gycrosskit/permission.git', :tag => '1.0.0'
```

```swift
import GycPermissionKuikly
import Shared // 按宿主既有 framework 名称导入

GycPermissionModule.configure {
    let handler = IosPermissionModuleHandler(platform: permissionPlatform)
    return (call: handler.call, dispose: handler.dispose)
}
```

`configure` 显式引用确切 `@objc(GycPermissionModule)`，SDK 按名称为当前 Renderer 创建 receiver；工厂每次创建新 handler。宿主仅提供既有能力和方法引用，不写 JSON、状态映射或取消 transport。Swift receiver 的 `invalidate` 立即失效，Main 异步释放，不阻塞 SDK 线程；Kotlin handler 在 Main 执行，JSON 字符串回执经 SDK ContextQueue 沿当前 callback 返回。实例不可跨 Renderer 复用。未配置 factory 或缺少 rootView 不会运行原生能力；未做设备与远程发布验收。
