## 本地行为检查

以下命令从仓库根目录执行。配置`ANDROID_HOME`与可运行Gradle的JDK；Kotlin/Native测试需要macOS、Xcode及iOS Simulator运行环境。Node测试转译真实ArkTS源码并使用受控SDK替身，`TYPESCRIPT_PATH`可指定已有TypeScript模块。

```sh
bash gradlew :permission-core:testDebugUnitTest :permission-core:compileKotlinIosSimulatorArm64 --max-workers=1
bash gradlew -p verification-kuikly test --max-workers=1
node --test ohos/permission-native/test/permission.test.cjs
```

只运行受影响目标；需要确认本轮真实执行时加`--rerun-tasks`，不要把`UP-TO-DATE`算成新执行。平台测试结果XML位于`permission-core/build/test-results/`；独立Module测试结果在`verification-kuikly/build/test-results/test/`。这些测试不调用真实分享、认证、拨号或定位业务。

## 结果与历史记录

源码 CI 使用固定 SHA 的 `gradle/actions/setup-gradle` 恢复依赖和编译产物；PR 只读缓存，
main 与手动源码验证可写入各自 ref 的缓存。现有 Kotlin/Native 工具链缓存独立保留。
仅 android/native job 开启 build cache；Gradle 行为测试禁用缓存和 up-to-date 跳过，
contracts、Swift receiver 生命周期、独立 staging consumer 与全部编译目标保持原入口。

冷暖对照使用同一已推送 SHA，串行运行两次统一远程验证；先核对首轮 Gradle 缓存 miss，
再核对第二轮 hit、编译任务的 `FROM-CACHE` 和两轮真实执行的测试 XML/日志。
已有 Kotlin/Native 工具链命中应单列，不能把首轮称为全工具链冷启动。排队、job 执行、
缓存读写和完整 workflow 耗时分别记录；单组冷暖对照不等于对旧方案的稳定提速比例。

本次候选的测试入口、实际执行平台、复用/新执行时点和未验收范围统一维护在[功能页验证范围](功能与平台差异.md#验证范围)。[权限历史验收](../verification/验收记录.md)、[0.1.3发布验收](发布验收-0.1.3.md)保留原记录时点，不证明当前候选已经发布或完成设备业务验收。

发布归档、不可变标签、checksum及远程消费要求见[共用发布流程](https://github.com/gycrosskit/.github/blob/main/docs/发布流程.md)。发布按当前不可变版本执行；验证不操作真实SDK业务。

## Native Module 候选检查

```sh
bash gradlew -p verification-kuikly test --max-workers=1
bash gradlew :permission-kuikly:compileReleaseKotlinAndroid :permission-kuikly:compileKotlinIosSimulatorArm64 --max-workers=1
# 发布到库内 staging 后，独立 verification-consumer 按 permissionMavenRepo / permissionVersion 消费。
```

`GycPermissionKuikly/Kuikly` 依赖真实 OpenKuiklyIOSRender 2.28.0，Swift receiver 必须用该 SDK 编译；不能用空 protocol 替身证明链接。source CI 在现有 native job 执行；远程不可变 tag 的 Git Pod 消费、设备权限/相机/定位仍是独立证据。

```sh
products=$(bash scripts/ci-build-kuikly-render.sh "$PWD/build/native-render" GycPermissionKuikly/Kuikly)
bash scripts/verify-kuikly-module.sh "$products"
bash scripts/verify-kuikly-assembly.sh "$products"
```

生命周期检查链接真实 Pod 与 SDK，执行真实 SDK `hrv_call` 接口、重复失效、排队调用、迟回调与 `TDFBaseModule.dealloc`；测试 handler 为受控闭包，rootView 为占位 UIView，不启动业务 Renderer。装配检查仅将本库候选发布到仓库内 staging，再从独立 consumer 导出 core/kuikly，使用生成的 Kotlin header 编译 Swift `call`/`dispose` 方法引用；不作为远程 Maven 或 Git Pod 消费证据。

仅 Native 工具链预热不恢复或保存源码 Gradle 缓存，避免预热先占用同 SHA 的不可变 Home key，阻止后续完整源码运行补写编译结果；原 Konan 预热入口、条件与门禁不变。

源码 CI 在缓存恢复与编译前选择 runner 已有的可用 iPhone Simulator，优先使用 Booted 设备，否则提前启动 Shutdown 设备，不额外创建或删除设备。准备步骤输出 UUID 和本轮是否启动的标记；module 仍等待 bootstatus，并验证本次 run_id 对应的 fresh receipt 与原 PASS。真实 Pod 构建后，module 生命周期和 assembly 装配检查并行执行，各自保存日志和耗时回执，必须两项都成功。CI 的 always 步骤卸载本轮检查 App，仅关闭本轮启动的设备；已有 Booted 设备保持运行。Native-only 预热和发布 job 不准备设备，独立命令的已有 Simulator 选择方式保留。

Native 源码 CI 保留固定版本 setup-gradle 的默认 transforms 缓存。Kotlin/Native 工具链解压与插件 instrumentation 都使用这类本地转换结果，不能只按缓存恢复步骤的耗时判断整轮收益。依赖、Wrapper、编译 build cache、Konan 与 Android/release 缓存策略保留，PR 仍只读缓存。

commonizer 的内部结果位于 Native home 的 `klib/commonized`，不由 setup-gradle 保存。源码 CI 在完整 Konan 恢复后单独恢复该目录；key 绑定工具链身份和 Gradle 版本/target 配置，保留 `.success` 并排除锁及临时文件。成功的非 PR 源码运行仅在两组 target 的成功标记齐全时保存新缓存，缺失时记录并跳过保存，不替代原源码门禁；PR 只读，工具链预热和发布 job 不使用此缓存。

assembly 的 staging 与 consumer 命令保留 `--info`、四个阶段标记和原任务，增加 `--profile` 及 `/usr/bin/time -lp`。Native 诊断 artifact 包含两个 Gradle root 的 profile 报告与 `assembly-*.time.txt`，用于区分配置、任务、wall/user/sys 和最大 RSS；计时不调整构建顺序、参数目标或错误退出码。time 的 CPU/RSS 以可统计的命令及被等待子进程为界，不代表 Gradle single-use daemon 或完整进程树的资源总量；阶段耗时结合 phase marker 与 profile 判断。计量仍包含新增缓存恢复/保存成本，首轮生成与次轮命中分别记录。

试点计量使用固定 SHA 串行完整源码验证，分别核对缓存命中、27 个实际执行 XML 用例、两项原生检查及清理回执；另记录准备、编译、ready、安装、启动与 receipt 阶段。两次命中缓存应称为暖/暖样本；与旧 main 的耗时差异包含 runner 和网络波动，不能将全部差异归因于重叠。
